# Деплой через GitHub Actions на self-hosted runner

Инструкция для репозиториев, где код доставляется на внутренний стенд, который
не виден облачным runner.

## Общая схема

| Что | Где находится | За что отвечает |
|---|---|---|
| Триггеры и порядок шагов | `.github/workflows/*.yml` | Когда запускать проверки и деплой |
| Переиспользуемый шаг деплоя | `.github/actions/<имя>/action.yml` | Как именно подключиться и обновить код |
| Приватный ключ | Secrets → Actions | Доступ раннера к стенду по SSH |
| Отпечатки хостов | Secrets → Actions | Защита от подмены сервера при SSH |
| Адреса и пути стендов | Variables → Actions | Подставляются в workflow без коммита |
| Сам runner | Settings → Actions → Runners | Исполняет задачи там, где виден стенд |
| Защита веток | Settings → Branches | Не даёт зайти в защищённую ветку без проверок |

Экшены в workflow зафиксированы по commitment SHA, а не по тегу: `uses:
actions/checkout@<sha> # vX.Y.Z`. При обновлении меняйте и SHA, и версию в
комментарии. Оба используемых экшена работают на Node.js 24 — предупреждение
про устаревший Node.js 20 в логах означало именно старые версии действий.

## 1. Ставим runner

### 1.1. Готовим токен и файлы

1. Заходим в **Settings → Actions → Runners → New self-hosted runner → Linux**.
2. Страница покажет команды скачивания под вашу архитектуру и **одноразовый
   registration token**. Скачиваем архив, распаковываем в отдельный каталог и
   переходим в него.
3. Токен живёт около часа. Если страницу открыли заранее, обновите её и
   скопируйте токен **перед самым запуском** `config.sh`. Просроченный или
   уже использованный токен даёт `404 Not Found` на registration-эндпоинт.
4. Проверяем на машине `bash`, `git`, `openssh-client` и `coreutils`
   (`base64`, `install` используются шагом деплоя).

### 1.2. Что спрашивает `config.sh`

Запуск: `./config.sh --url <URL репозитория> --token '<свежий_токен>'`

| Вопрос в терминале | Что это | Что лучше указать |
|---|---|---|
| Runner group | Группа раннеров; ей управляется доступ репозиториев | Обычно **Enter** → `Default` |
| Name of runner | Имя, под которым раннер виден в интерфейсе | Осмысленное уникальное имя `<роль>-<окружение>` |
| Additional labels | Метки для маршрутизации задач | **Enter**, если workflow не выбирает собственную метку |
| Work folder | Каталог временных файлов задач | **Enter** → `_work`; нужно достаточно места на диске |

После ответов увидите `√ Runner successfully added` и `√ Settings Saved.`

**Лучше так:** передавать ответы сразу флагами, чтобы не отвечать вручную:

```bash
./config.sh --url <URL репозитория> --token '<свежий_токен>' \
  --name <имя-раннера> --runnergroup Default --work _work --unattended
```

Стандартные лейблы `self-hosted`, `Linux`, `X64` добавляются автоматически.
У runner уровня репозитория в меню `…` может быть только `Delete`, без
`Rename`, поэтому имя стоит задать сразу.

### 1.3. Ставим службу

```bash
sudo ./svc.sh install
sudo ./svc.sh start
sudo ./svc.sh status
```

Все три команды выполняются через `sudo`: `svc.sh status` без `sudo` выведет
`Must run as sudo`. Если после `install` служба осталась `inactive (dead)` —
повторите `sudo ./svc.sh start` и посмотрите journalctl её юнита.

**Лучше так:** запускать runner как системную службу, а не в foreground, и не
давать ему root там, где это не нужно. После старта запись в списке раннеров
должна перейти в состояние `Idle`.

## 2. Задаём переменные стендов

**Settings → Secrets and variables → Actions → Variables → New repository variable**:

| Имя | Что содержит | Значение |
|---|---|---|
| `DEV_HOST` | адрес рабочего стенда | `<адрес>` |
| `PROD_HOST` | адрес основного стенда | `<адрес>` |
| `DEPLOY_USER` | пользователь для SSH | `<пользователь>` |
| `DEPLOY_DIR` | каталог рабочей копии на стенде | `<путь>` |

Workflow ссылается на них как `${{ vars.DEV_HOST }}` и т.д. Если каталоги на
стендах различаются, заведите `DEV_DIR` и `PROD_DIR` вместо общего `DEPLOY_DIR`
и поправьте блок `with:` в нужных job'ах.

**Лучше так:** адреса и пути держать в Variables, а не в файлах репозитория —
тогда workflow не раскрывает внутреннюю инфраструктуру, а смену адреса можно
сделать без коммита. Приватный ключ и отпечатки хостов хранятся в Secrets.

## 3. Готовим deploy-ключ и known_hosts

1. Создаём отдельную пару ключей — не используем свой рабочий ключ:

   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/<deploy_key> -N '' -C '<назначение>'
   ```

2. Публичный ключ добавляем на стенд в `~/.ssh/authorized_keys` пользователя,
   от которого будет идти деплой.
3. Проверяем доступ и passwordless sudo, если шаги деплоя обновляют права:

   ```bash
   ssh <пользователь>@<стенд> 'sudo -n true && echo sudo-ok'
   ```

4. Приватный ключ кодируем в одну строку:

   ```bash
   base64 -w0 ~/.ssh/<deploy_key>
   ```

   (в macOS: `base64 < ~/.ssh/<deploy_key> | tr -d '\n'`)

5. Фиксируем отпечатки хостов. `ssh-keyscan` принимает несколько хостов в одной
   команде, поэтому общий секрет для двух стендов собирается так:

   ```bash
   ssh-keyscan -H <dev-host> <prod-host> | grep -v '^#' > /tmp/deploy_known_hosts
   ssh-keygen -lf /tmp/deploy_known_hosts
   ```

   В файле будет по несколько строк на хост (RSA/ECDSA/ED25519) — это нормально.
   Если сканировать хосты отдельными командами, используйте `>>` для второго,
   иначе `>` перезапишет первый файл. Имена хостов должны совпадать с теми,
   что лежат в Variables: при смене IP на DNS нужно обновить записи.

6. **Settings → Secrets and variables → Actions → New repository secret**, два
   секрета, оба с включённым Masked:

   | Имя | Значение |
   |---|---|
   | `DEPLOY_KEY_B64` | вывод `base64 -w0` из шага 4 |
   | `DEPLOY_KNOWN_HOSTS` | содержимое `/tmp/deploy_known_hosts` целиком |

**Лучше так:** ключ только для CI, с минимально достаточным доступом, секреты
периодически ротировать. Отпечаток хоста сверяйте по доверенному каналу:
`ssh-keyscan` сам по себе не защищает от подмены, если делать его прямо во
время деплоя. В деплое включён `StrictHostKeyChecking=yes`: без секрета задача
упадёт до остановки сервиса, а не молча доверится чужому ключу.

## 4. Настраиваем workflow

- `push` в `dev` → проверки + деплой на dev-стенд;
- `push` в `main` → проверки + деплой на прод;
- `workflow_dispatch` с выбором цели → ручной повтор деплоя без изменений в git;
- `pull_request` → только проверки, деплой пропускается;
- деплой-задачи зависят от проверок через `needs: validate`;
- `concurrency` с `cancel-in-progress: false` не даёт двум деплоям одновременно
  делать `down`/`up` на одном стенде: повтор встаёт в очередь, а не прерывает
  начатый реимпорт;
- адрес, пользователь и каталог передаются в `with:` из Variables;
- на стенд перекатывается конкретный `github.sha`, а не «что сейчас в ветке»;
- после реимпорта проверяется здоровье с ожиданием, затем AMQP smoke на внешнем
  порту: TCP + `Connection.Start` с хоста, а не диагностика внутри контейнера.
  При провале любой проверки — откат на предыдущий коммит;
- если нужен доступ к продовому стенду только после подтверждения, используйте
  `environment` с обязательным approval.

**Лучше так:** проверки — общие для всех веток, деплой — только по push в
`dev`/`main` или явному `workflow_dispatch`. Если деплой на прод должен
подтверждаться вручную, заведите `environment` вместо автодеплоя.

## 5. Устраиваем composite action

Действие в `.github/actions/<имя>/action.yml` делает четыре вещи:

1. Кладёт ключ и `known_hosts` из секретов в уникальный для job каталог
   `$RUNNER_TEMP/.ssh` с правами `600` и `StrictHostKeyChecking=yes`.
2. Перед остановкой проверяет окружение на стенде: наличие `.env`, непустой
   cookie, `make`, `docker`, `docker compose`; снимает бэкап текущих definitions.
3. Фиксирует код на конкретном SHA и перезапускает сервис с перечитанием
   конфигурации:

   ```sh
   cd <каталог на стенде>
   git fetch origin <ветка>
   git checkout -q -B <ветка> <sha из github.sha>
   <команда перезапуска с перечитанием конфигурации>
   ```

4. Ждёт здоровья сервиса до 90 секунд: `docker compose up -d` возвращается
   раньше, чем прикладной процесс начинает отвечать на диагностику. Затем
   проверяет внешний AMQP-порт (`make test-connection`: TCP + `Connection.Start`),
   а не только `check_port_connectivity` внутри контейнера. При провале любой из
   проверок откатывается на предыдущий коммит. Ключ удаляется в финальном шаге
   с `if: always()`.

**Лучше так:** не хранить в репозитории `.env`, сгенерированные конфиги и
данные — они должны быть в `.gitignore`. Для сервисов, где конфигурация
читается только при старте, использовать перезапуск с реимпортом, а не обычный
`restart`.

## 6. Проверяем результат

1. Статус контейнера/сервиса и его здоровье на стенде.
2. Лог запуска: нет ли ошибок авторизации и прав доступа.
3. Автоматический AMQP smoke после деплоя плюс небольшая проверка основного
   сценария (одна операция, один запрос).
4. Если деплой меняет секреты — сначала обновить потребителей, затем проверить
   их подключение по логам.

## Частые ошибки

- Раннер не видит стенд — облачный runner вместо self-hosted.
- `Warning: Node.js 20 is deprecated` — экшены зафиксированы на старых тегах;
  обновить до версий на Node.js 24 и зафиксировать по SHA.
- `Permission denied (publickey)` — публичный ключ не добавлен или неверный
  пользователь.
- `Host key verification failed` — в `DEPLOY_KNOWN_HOSTS` нет записи для хоста
  из Variables либо запись снята для другого имени.
- `sudo: a password is required` — у пользователя нет passwordless sudo.
- `required variable is missing` — секрет/переменная не задана или пустая.
- Сервис поднялся, но конфигурация не применилась — использован `restart` вместо
  пересоздания с реимпортом конфигурации.
- `management.load_definitions invalid, file does not exist or cannot be read` —
  сгенерированный файл definitions недоступен контейнеру. Если он создан с
  правами `600` и принадлежит пользователю хоста, процесс внутри контейнера под
  другим uid не сможет его прочитать: нужны `640` и группа с uid процесса в
  образе.
- `node not running at all` сразу после `up -d` — проверка здоровья выполнена
  раньше старта процесса; нужен цикл с ожиданием, а не мгновенный провал.
